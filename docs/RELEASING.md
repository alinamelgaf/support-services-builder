# Выпуск новой версии

1. Обновите номер в `package.json`. Используйте новый номер `X.Y.Z` для каждого выпуска, включая выпуск с откатом поведения.
2. Добавьте первым разделом в `CHANGELOG.md` строку `## X.Y.Z — YYYY-MM-DD` и подразделы «Добавлено», «Изменено», «Исправлено». Укажите хотя бы одно конкретное изменение. Пустую категорию обозначьте тире. Для проверки выполните `pnpm check:release`.
3. Выполните `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm build` и проверку публичной поставки с частным списком. Отправьте коммит в основную ветку после review и дождитесь зелёного CI.
4. Создайте тег `vX.Y.Z` на проверенном коммите и сохраните черновик стабильного GitHub Release с этим тегом.
5. Вручную запустите **Publish an approved release** из основной ветки с этим тегом. Проверьте результат браузерных тестов и одобрите защищённые окружения. Релизный workflow сверит номер, аудит зависимостей, исходники и сборку, прогонит PWA на HTTPS, приложит архивы и опубликует описание изменений. Собирать ZIP вручную для GitHub не требуется.
6. Проверьте страницы Releases и Pages. Убедитесь, что установленный экземпляр предлагает новую версию, после подтверждения восстанавливает предложение и показывает изменения нужного выпуска.

Если упала сборка или тесты, исправьте причину в проверяемом коммите до публикации. Уже опубликованный тег сохраняйте неизменным. Если публикация релиза успешна, а Pages завершился ошибкой, повторите только упавшее задание Pages из того же запуска. [Документация GitHub CLI для обновления релиза](https://cli.github.com/manual/gh_release_edit)
