# Публикация на GitHub

Поставка подготовлена локально. Для публикации нужно отдельное решение владельца. Исходники, документацию, зависимости и оба артефакта проверьте перед первым push. Лицензию на собственный код определяет владелец. Лицензии стороннего кода приведены в `THIRD_PARTY_NOTICES.txt` сборок.

## Проверка перед публикацией

1. Подготовьте вне проекта частный список корпоративных названий, доменов, меток и других характерных строк. По одной строке на запись. Задайте локально переменную `SSB_PRIVATE_DENYLIST` с путём к этому файлу.
2. В чистом рабочем каталоге запустите `pnpm install --frozen-lockfile`, `pnpm audit --audit-level low`, `pnpm test`, `pnpm build`, `node scripts/check-public.mjs --built --private-required`, `pnpm test:browser` и `pnpm package`. Для браузерного теста установите Chromium через Playwright или выберите установленные Chrome и Edge переменной `SSB_BROWSER_CHANNELS=chrome,msedge`.
3. Сверьте состав `git ls-files`, `dist/` и ZIP. Просмотрите различия после последней проверки, историю Git и отчёт безопасности. Корпоративные строки из частного списка, импортированные данные и снимки рабочих документов храните вне GitHub.

## После разрешения владельца

1. Создайте репозиторий `support-services-builder`. Отправьте только новый проект. Если используете ZIP исходников, распакуйте его, инициализируйте Git и создайте начальный коммит с проверенными файлами. Настройте обязательные проверки CI и ограничьте создание и изменение релизных тегов.
2. В **Settings → Pages** выберите **GitHub Actions**. Создайте окружения `public-release` и `github-pages` и установите требование ручного одобрения, если тариф GitHub это поддерживает. Доступ к запуску релиза должен быть у ответственных за выпуск. Включите `SSB_PUBLIC_RELEASE_ENABLED=true` только после согласования публикации. [Настройка GitHub Pages через Actions](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
3. Поднимите версию в `package.json`, проверьте изменения, создайте защищённый тег `vX.Y.Z` и черновик стабильного GitHub Release для этого тега. В **Actions → Publish an approved release** запустите workflow на основной ветке с тем же тегом.
4. После проверки артефактов одобрите выпуск. Workflow сверяет commit тега и статус черновика, проверяет контрольные суммы, прикрепляет ZIP, публикует релиз и затем выкладывает PWA. Если Pages прервался после успешного выпуска, повторно запустите только упавшие задания.

CI для веток и pull request запускает сканирование, аудит зависимостей, автоматические тесты и упаковку. Рабочие данные пользователей для CI не нужны. Workflow выпуска требует ручного запуска, проверенного тега, черновика стабильного релиза и включённой переменной. Администраторам нужно отдельно настроить права и защиту окружений в GitHub.
