# Первая публикация Support Services Builder на GitHub

Подготовленная версия для первого релиза — **1.1.0**. Решение о публикации и лицензию исходников принимает владелец. Добавьте `LICENSE` после выбора лицензии. Лицензии зависимостей включены в сборки.

## Перед загрузкой на GitHub

1. Откройте актуальный локальный проект или распакуйте ZIP исходников. Если используете ZIP, инициализируйте новый Git-репозиторий командой `git init -b main` и добавьте проверенные файлы.
2. Держите список корпоративных маркеров вне проекта, по одной строке на запись. Задайте `SSB_PRIVATE_DENYLIST` с путём к нему. После установки зависимостей выполните `pnpm build` и `node scripts/check-public.mjs --built --private-required`.
3. Просмотрите `git ls-files` и историю. Публичный проект содержит только синтетические данные. Коммит с версией, изменениями и выбранной лицензией должен быть готов до создания тега.

## После согласования публикации

1. Создайте пустой публичный репозиторий **support-services-builder**. Отправьте чистую ветку `main` проекта. При использовании локального репозитория добавьте адрес нового репозитория как `origin`.
2. В **Settings → Pages → Build and deployment** выберите **GitHub Actions**. В **Settings → Environments** настройте `public-release` и `github-pages`. Разрешите выпуск с основной ветки и включите требование ручного одобрения, если оно доступно для вашего плана. Ограничьте права на теги релизов. [Настройка GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
3. В **Settings → Secrets and variables → Actions → Variables** создайте переменную `SSB_PUBLIC_RELEASE_ENABLED` со значением `true`.
4. Дождитесь успешного workflow **Validate source and builds**. Создайте и отправьте тег `v1.1.0` на проверенном коммите. В **Releases → Draft a new release** выберите этот тег и сохраните стабильный релиз как черновик.
5. В **Actions → Publish an approved release → Run workflow** выберите основную ветку и укажите `v1.1.0`. Одобрите задания в защищённых окружениях. Workflow сам собирает архивы, добавляет описание из `CHANGELOG.md`, публикует GitHub Release и затем развёртывает Pages.
6. Откройте адрес из шага Pages. Проверьте номер версии, «Что нового», «Помощь» и установку в Chrome и Edge. После проверки передайте ссылку менеджерам.

Следующий выпуск выполняется по [инструкции выпуска](RELEASING.md).
